# plan.md — Implementation Roadmap (v2)

Companion to `CLAUDE.md` (architecture, conventions, data model, known pitfalls) and `assignment.md` (original brief). Total budget: ~24h.

## Ordering principles

1. **Deploy the walking skeleton in Phase 0.** Supabase pooling, `prisma generate` on Vercel and env vars are the things that break, and they must break at hour 2, not hour 22.
2. **Buyer browse before Seller forms.** `/buyer/assets` is the screen a reviewer opens first and compares to `n5deal.com/all-listing`. Build it early on seeded data.
3. **Every phase ends deployable.** Push after each phase; never accumulate a big unverified diff.

- [x] `/buyer/assets` — server-side list with filters via `searchParams`: search, country, category, industry, price range — *explicit `select` rather than whole rows: `description` is up to 2000 characters per card and is never rendered here. - [x] Filter bar as a Client Component writing to `searchParams` (URL is the state → survives refresh, shareable, no client store) — *URL⇄query translation lives in `filters.ts` and every value is validated against `taxonomy.ts`, dropped rather than rejected. ### Phase 5 — Seller flows (3h)

- [x] `/seller/assets` — own listings table, status badges — *a table, not `AssetCard`: the card returns `null` for anything not ACTIVE (it defends buyer browse against leaking a moderated listing), and this is the one screen where a seller has to see their suspended rows. Carries an inquiry count per listing (`_count`), which is the number a seller actually comes here for. No filter bar — nothing in the brief asks for one over a seller's own inventory.*
- [x] New/Edit asset — **single form**, category `Select` at the top, conditional block via `watch("category")`. Zod discriminated union + `z.coerce`. `sanitizeByCategory()` before update. — *`useWatch`, not `watch()` — the latter returns a fresh function each render and makes React Compiler skip memoizing the largest component in the app. react-hook-form cannot hold a discriminated union as `TFieldValues` (`UseFormReturn` is invariant in it), so the form registers against a flat superset type and the union still does the validating, at the cost of one commented cast on the resolver. Switching category clears all five category columns and their errors — `annualRevenue` is shared by two branches, so "clear only the outgoing branch" has no single right answer; leaving stale errors on unrendered fields makes Save look broken. Two deliberate additions to the schema in `CLAUDE.md`: human-readable messages, and `.max(2_147_483_647)` on the money/int fields — Postgres `Int` is 32-bit and the snippet as written lets `9999999999` through Zod and into an uncaught driver error.*
- [x] `/seller/buyers` — buyer list + filters (industry, region, budget) — *cards, not a table: a mandate is chips plus prose, which a table flattens. `role: "BUYER", status: "ACTIVE"` is baked into the where and can never be widened by the query string. Budget is one number ("who could afford this?") matched against both of a buyer's bounds, with an absent bound read as open-ended rather than zero — the same asymmetry Phase 7's `computeMatchScore` will apply. That reading is written down once, in `components/seller/format-budget.ts` (`{ compact }` shape borrowed from `categoryFacts()`), because the card and the profile page both render the range and two copies is how it gets corrected on one surface only. No email anywhere on this screen or the profile: the seller opens the conversation through an inquiry, and the address is revealed when the buyer replies.*
- [x] `/seller/buyers/[id]` — profile view + "Contact Buyer" — *`notFound()` for anything that is not an ACTIVE buyer, so a suspended account is indistinguishable from one that never existed — the same rule the listing detail page applies. The list's filters ride along on the URL and are re-parsed on arrival, so "Back to buyers" restores the list the seller had without the link being able to carry a hand-edited filter back.*
- [x] `/seller/inquiries` — Sent / Received — *defaults to Received, where the buyer's twin defaults to Sent: a buyer arrives having just written to someone, a seller arrives to see who asked about their listings. Its card is a near-twin of the buyer's under `components/seller/`, differing only in link targets (`/buyer/assets/[id]` is a route `requireRole` would bounce a seller out of) — see the note below on merging the two.*

**Added, not in the original plan:** `deleteAsset` — a **soft** delete (`listingStatus: "REMOVED"`), surfaced as "Withdraw listing". `Inquiry.asset` is an optional relation with no explicit `onDelete`, so Prisma defaults to `SetNull`: a hard delete would silently rewrite history, turning a buyer's sent message into "General enquiry — no listing" long after they wrote it about a specific asset. No `AuditLog` row either — `lib/audit.ts` records *manager moderation*, and a REMOVE_ASSET entry with a seller as its actor would put ordinary housekeeping into the moderation table on `/manager`.

**Left for a consistency pass after this merges** (the same kind the `ActionResult`/category-badge pass did after Phases 3/4/6, and deliberately not done here because it means editing files outside this phase's lane): fold `components/{buyer,seller}/inquiry-card.tsx` + `inquiry-list.tsx` into one `components/inquiry/` taking an `assetHref` prop, and lift the duplicated `MESSAGE_MIN`/`MESSAGE_MAX` out of the two `inquiry-schema.ts` files. — *done in Phase 7. The pass also found what the duplication had already cost: the two pages' `preview()` helpers had drifted, the seller's cutting by code point and the buyer's by UTF-16 code unit, so an emoji at the cut rendered as "�" on one screen and not the other. Both now call `previewMessage` from `lib/inquiry-message.ts`.*

- [x] `/manager` — counters + latest audit-log entries — *four stat cards (Total Buyers/Sellers, Active Listings, Suspended+Removed Users) plus a raw Table (Actor/Action/Target Type/Target ID/Date) of the last 10 `AuditLog` rows, sorted desc*
- [x] `/manager/participants` — table, search/filter by role/status, Suspend / Remove / Reactivate — *lists Buyers and Sellers only, per the brief's "see Buyers, Sellers, and Assets"; a clean state machine (Suspend only from ACTIVE, Remove from ACTIVE/SUSPENDED, Reactivate only from SUSPENDED — REMOVED is terminal) decides which actions a row offers*
- [x] `/manager/assets` — table, search/filter, Suspend / Remove — *no Reactivate: `plan.md` and the `AuditAction` enum both scope assets to Suspend/Remove only, so a manually-suspended listing has no path back to ACTIVE in this build — a deliberate scope cut*
- [x] Seller status change cascades to their assets in one Prisma transaction — *Suspend/Remove/Reactivate each bulk-update only the assets that transition matters for, so a manager's direct asset-level moderation is never silently undone. Reactivate is the subtle one: "assets left SUSPENDED by the cascade" excludes a listing a manager suspended on its own merits, told apart by whether it has a `SUSPEND_ASSET` audit row of its own — exact only while there is no asset-level Reactivate; see the note on `restoreCascadedListings`*
- [x] Guards: a manager cannot suspend/remove themselves or another manager — *enforced in the Server Actions (`app/manager/{participants,assets}/actions.ts`), not just hidden in the UI*
- [x] `logAction()` writes an `AuditLog` row inside the same transaction — *`lib/audit.ts`; also deletes the target's `Session` rows on Suspend/Remove (CLAUDE.md → Auth) so an open session dies immediately rather than waiting out the 60s cookie cache*

### Phase 7 — Smart Matching (1.5h)

- [x] `lib/matching.ts` → `computeMatchScore(profile, asset): number` (pure) — *no runtime imports at all: `MatchProfile`/`MatchAsset` are declared structurally, so a Prisma row satisfies them without a cast and the module needs neither the client nor the path alias. It also carries `bestMatchScore` (the seller's "best across my inventory") and `compareByMatchDesc` (the shared "score desc, unscored last" comparator), because both screens need the same two rules and one of them would otherwise be written twice.*
- [x] Vitest + ~6 unit tests: full match, zero match, partial, missing budget bounds, empty arrays, price on the boundary — *15 tests. The baseline fixture is a **full** match, so every partial case is expressed by breaking exactly one thing. Added beyond the list: an inverted range (`budgetMin > budgetMax`, which nothing validates at the profile level) scores 0 for price, plus coverage of `bestMatchScore` and the comparator. Needed a `vitest.config.mts` — the repo had none, and `npm test` had never actually run anything. `.mts`, not `.ts`: without `"type": "module"` a `.ts` config loads as CommonJS and Vite warns (pitfall 15).*
- [x] Match badge on asset cards (buyer side) and buyer cards (seller side) — *the badge itself moved out of `asset-card.tsx` into `components/match/match-badge.tsx`; two copies of the banding is how one of them gets corrected alone. Its `title` is a required prop, because the number is meaningless without saying what it was scored against and that sentence differs per role.*
- [x] "Recommended for you" section + "Best match" sort — *the section renders only on the untouched view (`!hasActiveFilters && sort === DEFAULT_SORT`), out of the array already fetched — no second query. Once a buyer filters or sorts they have stated intent, and a top-3 strip would just repeat the first cards of the grid at them. Both "Best match" sorts are stable JS re-sorts layered on the SQL ordering (newest first), so equal scores stay newest-first rather than arbitrary.*
- [x] No-profile fallback: hide badges, show "complete your profile" prompt — *and its mirror on the seller side: a seller with no listings has nothing to score buyers against, so they get "Publish a listing to see how well buyers match it" instead of silently missing badges. In both cases the "Best match" option is removed from the sort dropdown and a hand-typed `?sort=best-match` falls back to the default — the bar can never offer a sort the list is not applying. The buyer half was unreachable at first (the seed gave all 8 buyers a profile), so `prisma/seed.ts` now leaves `buyer.silva@demo.com` without one and names that account in its closing output — Zielińska keeps hers because it is the only profile with both budget bounds null. Re-seeded and verified; the seller half needs no seed change, since Silva's card now carries no badge and sorts last.*

### Phase 8 — AI search (1.5h)

- [x] `POST /api/ai/parse-query` — free-text → `{ search?, country?, industry?, category?, priceMin?, priceMax? }` as strict JSON, validated with Zod — *uses the official `@anthropic-ai/sdk`, not raw `fetch`. Model is `claude-sonnet-5`, not the `claude-sonnet-4-6` named when this phase was originally scoped — current-generation and cheaper ($2/$10 vs $3/$15 per 1M tokens) for a parsing task this small. `country`/`industry` are enumerated exactly in the system prompt (not just described) after a review caught that "drop non-matching values downstream" isn't the same as "help the model produce a matching value" — a first pass that omitted the taxonomy let the model return "Western Europe" or "crypto", both of which read the query correctly but fail `filters.ts`'s exact-match `oneOf()` and vanished with no signal. Per-field Zod (`.optional().catch(undefined)`) so one bad field can't discard five good ones — the same "drop, don't reject" rule the rest of the app applies to a hand-edited URL.*
- [x] Wire it into the existing buyer filter bar: parsed values simply populate `searchParams`, so the whole downstream path is already built and tested — *`AiSearchBar`, a colocated subcomponent in `asset-filter-bar.tsx` (same pattern as `FilterSelect`/`PriceInput`), writes only the keys the AI response actually returned — a manually-set filter the query didn't mention (e.g. Country) survives an AI search rather than being cleared. An empty `{}` result (nothing extracted, not a failure) falls back to a plain search of the raw query instead of silently doing nothing. The bar also re-checks `country`/`industry` against `taxonomy.ts` client-side before writing them — belt-and-braces on top of the prompt fix above, since a model can still slip — and shows a "couldn't match every detail" note when it drops something, rather than letting a filter disappear with no explanation, which was the one place in the app where *this code* (not a hand-edited URL) could put the bar and the list out of sync.*
- [x] Fallback on error/timeout/invalid JSON: treat the input as a plain text search, show a small "AI unavailable, using text search" note. **Demo must never break because of this feature.** — *verified end to end with no `ANTHROPIC_API_KEY` configured locally (the SDK throws on the first call, caught, returns the fallback JSON): the page never errors, `search` gets the raw query, and the note renders. The route itself never returns a non-200 for an AI *mechanics* failure — always `{ fallback: true, search }` at 200 — so the client has one branch instead of also handling non-2xx. Authentication (see below) and a malformed body are the deliberate exception: those are protocol errors, not the AI failing, and get a real 401/400 that the client's `response.ok` check folds into the same fallback UI.*
- [x] Two example chips under the input so a reviewer can try it in one click — *pre-fill only, matching "click to try" rather than auto-submitting on click*
- [x] **Added after a review, not in the original scope:** the route had no auth check — `POST /api/ai/parse-query` was reachable by anyone with the URL, sessions or not, making it an open proxy to a paid API billed to this project's key. `src/proxy.ts` only matches `/buyer|/seller|/manager`, and the three-layer access control CLAUDE.md describes (proxy → role layout → action) never accounted for a route handler outside that list. Fixed with `getSessionUser()` (not `requireRole()`, which `redirect()`s — wrong for a fetch caller expecting JSON) gating on `role === "BUYER" && status === "ACTIVE"`, returning `401` otherwise. No rate limiting beyond that: an in-memory per-user counter would be close to a no-op on Vercel's stateless functions (a cold instance shares no memory with the last one), and real rate limiting needs a store this project doesn't otherwise have — left as a known gap, not a silent one.

## Assumptions log (condensed — full reasoning goes in the README)

1. Auth: full Better Auth + 3 seeded users, not a no-login role switcher.
2. `Asset` fields aren't in the brief — modeled from its "M&A opportunities and financial assets" framing, not copied 1:1 from the narrower reference site.
3. `Asset.category` (License / Operating Business / Stake) added — not on the reference site, needed because the written brief is broader than license trading.
4. Contact flow = a single `Inquiry` record, not live chat.
5. The brief gives a profile to Buyer only — Seller gets one optional `companyName` field instead of a full table.
6. `SUSPENDED` = reversible soft block, `REMOVED` = soft delete; both cascade to a Seller's assets at the application level.
7. Money is `Int` in whole EUR, single currency, no conversion.
8. View counters / favourites from the reference site excluded — not in the written brief.
9. Matching is deterministic and rule-based so it's reproducible during review; the one LLM feature (query parsing) is additive and degrades to plain search.
